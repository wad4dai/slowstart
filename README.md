# slowstart

Скрипт для замера скорости скачивания со своего компьютера. На вход принимает адрес
тяжёлого файла, делает к нему 10 последовательных запросов, каждый раз дожидается
полного ответа и печатает:

- сколько запросов прошло успешно;
- среднее время запроса;
- общий объём скачанных данных;
- среднюю скорость в MB/s и Mbit/s.

```console
uv slowstart https://upload.wikimedia.org/wikipedia/commons/3/3f/Fronalpstock_big.jpg
```

![demo](docs/demo.gif)

## Откуда название

**TCP slow start** — механизм, с которого начинается каждое TCP-соединение.
Отправитель не знает, какую скорость выдержит канал, поэтому начинает с маленького
окна перегрузки (обычно около 10 сегментов, ~14 KB, RFC 6928). Затем окно
удваивается на каждый RTT, пока не случится потеря пакета или не будет достигнут порог.

Для замера скорости это главный источник искажений:

- **Маленький файл целиком скачивается ещё во время разгона.** Получается замер
  задержки (RTT), а не пропускной способности канала.
- **Каждое новое соединение разгоняется заново.** По умолчанию slowstart открывает
  новое соединение на каждый запрос, поэтому в каждый замер честно входят DNS,
  TCP-рукопожатие, TLS и разгон. Так ведёт себя обычная загрузка файла в браузере
  или через `curl`. Флаг `--reuse-connection` включает keep-alive, и тогда эти
  накладные расходы остаются только в первом запросе.

Поэтому для замера нужен файл покрупнее, от 10–50 MB (подробнее в разделе
[Ограничения](#ограничения)).

## Установка

Нужен Python 3.11+.

**uv**

```bash
git clone https://github.com/wad4dai/slowstart.git
cd slowstart
uv sync
uv run slowstart --help
```

Или поставить как отдельную утилиту:
`uv tool install git+https://github.com/wad4dai/slowstart.git`.

**pip**

```bash
git clone https://github.com/wad4dai/slowstart.git
cd slowstart
python3 -m venv .venv
source .venv/bin/activate
pip install .
slowstart --help
```

Запуск без установки entry point: `python -m slowstart ...`.

## Использование

```bash
slowstart <url> [опции]
```

| Опция                | По умолчанию | Что делает                                                                   |
|----------------------|--------------|------------------------------------------------------------------------------|
| `-n`, `--count`      | `10`         | Сколько запросов сделать                                                     |
| `--timeout`          | `30`         | Таймаут в секундах на каждую сетевую операцию (см. ниже)                     |
| `--reuse-connection` | выкл.        | Переиспользовать соединение (keep-alive)                                     |
| `--no-cache-bust`    | выкл.        | Не добавлять к URL уникальный query-параметр                                 |
| `--plain`            | выкл.        | Простой текстовый вывод без прогресс-баров и цветов (для логов, cron и CI)   |

Если в URL есть `?` или `&`, возьмите его в кавычки. Иначе zsh или bash
попытаются разобрать эти символы сами.

### Ошибки и коды выхода

Неуспешный запрос (ответ не 2xx, таймаут, обрыв соединения) не прерывает прогон.
Печатается причина, а сам запрос не попадает в статистику:

```text
Запрос  3/10: ошибка — timeout после 30 s (сервер перестал отдавать данные)
...
Успешно: 9/10
```

| Код   | Когда                                                                       |
|-------|-----------------------------------------------------------------------------|
| `0`   | Хотя бы один запрос успешен                                                 |
| `1`   | Ни один запрос не завершился успешно                                        |
| `2`   | Невалидный URL или опции                                                    |
| `130` | Прервано по Ctrl+C: статистика печатается по уже завершённым запросам       |

## Как считается

**Формула**

```text
средняя скорость = Σ байт успешных запросов / Σ времени успешных запросов
```

Здесь берётся сумма, делённая на сумму, а **не** среднее арифметическое скоростей
отдельных запросов. Пример: два запроса по 10 MB, один занял 1 s, другой 9 s.
Реально скачано 20 MB за 10 s, то есть 2 MB/s. Среднее скоростей дало бы
(10 + 1.1) / 2 ≈ 5.6 MB/s: быстрый запрос весил бы столько же, сколько
медленный, хотя занял в девять раз меньше времени.

Среднее время запроса считается как Σ времени / число успешных запросов.

**Единицы**: десятичные, как у провайдеров и в сетевом оборудовании.
1 MB = 10⁶ байт, 1 Mbit = 10⁶ бит, Mbit/s = MB/s × 8.

**Что входит во время.** Таймер (`time.perf_counter()`, монотонный и с высоким
разрешением, в отличие от `time.time()`) запускается перед отправкой запроса и
останавливается после получения последнего байта тела. По умолчанию в это время
входят DNS, TCP, TLS и редиректы: slowstart за ними следует, как браузер. Закрытие
соединения в замер не входит.

**Почему не `Content-Length`.** Считаются байты, которые реально пришли из сети.
Заголовок может отсутствовать, быть неверным, а соединение может оборваться на
середине. Тело читается потоком (`iter_raw`) кусками по 64 KiB и в памяти не
хранится. Если пришло меньше заявленного, это ошибка «обрыв соединения», а не
успешный замер.

**Зачем `Accept-Encoding: identity`.** Если сервер сожмёт ответ gzip/br, по сети
пройдёт меньше байт, чем весит файл. Тогда либо скорость окажется завышенной (если
считать распакованные байты), либо замер будет зависеть от степени сжатия
конкретного файла. `identity` просит отдать файл как есть, а `iter_raw` считает
именно сетевые байты без распаковки, даже если сервер всё равно сожмёт ответ.

**Зачем cache-busting.** По умолчанию к URL добавляется параметр
`_slowstart=<uuid>`, уникальный для каждого запроса. Существующий query
сохраняется. Вместе с заголовком `Cache-Control: no-cache` это не даёт отдать файл
из кэша прокси или браузерного кэша ОС. Некоторые серверы и подписанные ссылки
не принимают лишние параметры, для них есть `--no-cache-bust`.

**`--reuse-connection`.** По умолчанию keep-alive выключен: каждый запрос открывает
новое соединение. Клиент при этом один, чтобы не пересоздавать SSL-контекст на
каждый запрос: это время CPU, а не сети. С флагом соединение переиспользуется.
Первый запрос получается «холодным», остальные идут без рукопожатий. Разница между
двумя режимами показывает, сколько стоят установка соединения и разгон TCP на
вашем канале.

**Таймаут** ограничивает каждую сетевую операцию, а не весь запрос: установку
соединения и ожидание очередной порции данных. «30 s без единого байта» считается
ошибкой. Медленная, но идущая загрузка большого файла при этом не обрывается и
остаётся валидным замером.

**Прочее**

- **User-Agent.** Отправляется `slowstart/<версия> (+ссылка на репозиторий)`:
  некоторые сайты, например Wikimedia, отказывают клиентам без понятного UA.
- **Прогресс-бар не влияет на замер.** Функция замера ничего не знает про Rich и
  только вызывает callback с числом полученных байт. Отрисовка идёт в фоновом
  потоке Rich примерно 10 раз в секунду. В режиме `--plain` callback'ов нет вовсе.

## Ограничения

- **Размер файла.** На маленьких файлах результат определяется задержкой (RTT,
  рукопожатия, разгон TCP), а не пропускной способностью. Файл на 100 KB через
  канал с RTT 50 ms покажет «скорость» во много раз ниже реальной. Используйте
  файлы от 10–50 MB, а на быстрых каналах (от 500 Mbit/s) и крупнее.
- **Это скорость до конкретного сервера, а не «скорость интернета».** На результат
  влияют маршрут, загрузка и ограничения этого сервера, пиринг вашего провайдера
  и RTT до него. Другой сервер покажет другое число.
- **CDN.** Крупные файлы обычно отдаёт ближайший узел CDN, так что вы измеряете
  скорость до него. Cache-busting может заставить CDN сходить за файлом к origin,
  и первые запросы окажутся медленнее. Некоторые CDN, наоборот, игнорируют query
  в ключе кэша.
- **Одно TCP-соединение.** Speedtest-сервисы качают в несколько параллельных
  потоков, чтобы гарантированно загрузить канал. Здесь запросы строго
  последовательные: это честная скорость одной загрузки, но на каналах с большим
  RTT × пропускная способность она может оказаться ниже тарифа.
- **DNS** может кэшироваться операционной системой, поэтому в последующих запросах
  он почти ничего не стоит даже без keep-alive.
- Используется HTTP/1.1 (httpx без HTTP/2).

## Разработка

```bash
uv sync                      # зависимости, включая dev-группу (pytest, ruff)
uv run pytest                # тесты
uv run ruff check .          # линтер
uv run ruff format --check . # проверка форматирования
```

Через pip: `pip install -e . pytest ruff`. С pip 25.1+ можно использовать
`pip install -e . --group dev`.

Тесты не ходят в интернет. Они поднимают локальный `http.server` на свободном
порту в отдельном потоке и проверяют:

- точный подсчёт объёма;
- ответ без `Content-Length`;
- 404, таймаут, обрыв и редирект;
- заголовки запроса;
- новое соединение на каждый запрос или переиспользование одного;
- формулу средней скорости;
- cache-busting;
- CLI: коды выхода, `--plain`, Ctrl+C.
